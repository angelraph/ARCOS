# Circle Product Feedback

_Living document — updated throughout the build, not written after the fact._

## Why we chose these products

- **`@circle-fin/developer-controlled-wallets`** — lets ARCOS's agents sign and submit real contract transactions (TreasuryPolicy, Escrow, DecisionLedger) without any agent process ever holding a raw private key. That property is central to ARCOS's pitch: autonomous agents moving real USDC needs to be safely custodied, not just "fast."
- **`@circle-fin/x402-batching` (Circle Nanopayments)** — the Procurement Agent pays a real, gasless, sub-cent, EIP-3009-signed micropayment via Circle Gateway to obtain the Supplier Agent's quote (`apps/agents/src/gateway/`). This is the natural settlement rail for agent-to-agent commerce at high frequency, which is exactly ARCOS's Track 4 scenario — the bulk purchase itself still goes through Escrow, since that leg needs hold/release/refund semantics x402 doesn't provide, but the negotiation fee is a real Gateway payment, not a mock. Settlement is confirmed working end to end on Arc Testnet after two SDK/config fixes (see "What could be improved") — the flow still falls back to an unpaid quote if a given payment fails for an ordinary reason (insufficient Gateway balance, a facilitator hiccup), by design, not because settlement is broken.
- **`@circle-fin/app-kit` (Bridge Kit, CCTPv2)** — a minimal cross-chain treasury rebalance demo (`apps/agents/src/bridge/treasuryBridge.ts`, `scripts/bridge-treasury-demo.ts`): bridges idle Arc Testnet USDC to another CCTPv2-supported chain via `BridgeKit.bridge()`, using Circle's Orbit relayer (`useForwarder: true`) so no destination-chain gas wallet is needed. Chosen over wiring CCTP v2 and Gateway separately because Bridge Kit's `kit.bridge({ from, to, amount })` collapses approve → burn → attestation → mint into one call with typed step-by-step results.

## What worked well

- `initiateDeveloperControlledWalletsClient` + `createWalletSet`/`createWallets` worked first try against `ARC-TESTNET` — created a 5-wallet set (Treasury/Procurement/Supplier/Governance/Customer) in one call, addresses came back immediately, no propagation delay.
- Cloning the two official sample repos (`arc-nanopayments`, `arc-escrow`) and reading their actual source (not just docs) was the single highest-leverage research step — it surfaced the real `createContractExecutionTransaction` call shape and the real Arc Testnet USDC address (`0x3600...0000`) faster than the docs alone did.
- `createGatewayMiddleware` + `GatewayClient` worked exactly as documented for the whole handshake: an unpaid request correctly returned 402 with payment requirements (in the `PAYMENT-REQUIRED` header), `GatewayClient.pay()` correctly discovered them, built and EIP-712-signed the EIP-3009 authorization, and submitted it to Circle's real Gateway facilitator. With a deliberately unfunded test key it correctly rejected for insufficient Gateway balance — the right failure at the right layer, proving the whole handshake is genuinely exercised, not mocked. **Update:** after upgrading to `@circle-fin/x402-batching@3.2.0` and fixing the testnet facilitator URL (see below), a funded key now settles for real — `GatewayClient.getBalances().gateway.available` dropped from `1.00` to `0.98` after a `$0.02` `pay()` call, confirmed independently via Circle's transfer-search API (`status: "received"`, real transfer `id`). See "What could be improved" for the two bugs that stood between here and there.
- **`BridgeKit.bridge()` worked perfectly end to end on the first real attempt, no debugging required.** Funded a fresh EOA on Arc Testnet (20 native gas + 20 USDC via `faucet.circle.com`), then ran `kit.bridge({ from: { adapter, chain: "Arc_Testnet" }, to: { recipientAddress, chain: "Base_Sepolia", useForwarder: true }, amount: "1.00" })`. All four steps (`approve`, `burn`, `fetchAttestation`, `mint`) reported `state: "success"` with real tx hashes on both chains — and we independently re-verified on Base Sepolia via a plain `balanceOf` RPC call (not just trusting the SDK's own report): the address's USDC balance went from 0 to `0.946727` (exactly $1 minus the CCTP relayer's `feeExecuted` of 0.053273 USDC), and the mint tx (`0xc80ccb4...`) shows `status: success` directly from `eth_getTransactionReceipt`. Arc Testnet → Base Sepolia is a fully working, forwarder-relayed CCTPv2 route today.

## What could be improved

- **`Blockchain` type in `@circle-fin/developer-controlled-wallets` (v4.7.0) doesn't include `"ARC-TESTNET"`** in its exported union, even though the runtime API accepts it and returns real Arc addresses. Had to cast past the stale type (`scripts/create-wallets.ts`) rather than get a clean compile. Minor, but it's exactly the kind of thing that makes a first-time integrator second-guess whether they're calling the SDK correctly.
- Two separate "USDC"s on Arc are easy to conflate: the native gas token (18 decimals, used automatically for tx fees, funded by the public faucet) vs. the ERC-20 commerce USDC at a fixed address (6 decimals, what `TreasuryPolicy`/`Escrow` actually move). Nothing in the Arc docs landing page flags this distinction up front — we only found it by reading `arc-nanopayments/agent.mts`'s use of `parseEther` (native) alongside `erc20Abi.transfer` (commerce) side by side.
- The public web faucet (`faucet.circle.com`) and the Developer Console's wallet-ID-based faucet are two different tools with overlapping purpose and no cross-linking between their docs pages — cost us a round trip pasting a wallet ID into a field that expected an address instead.
- `npm.com` and some `developers.circle.com` pages return HTTP 403 to non-browser fetches, which made verifying exact SDK method signatures (e.g. entity-secret rotation) harder than it needed to be during a time-boxed build.
- **RESOLVED — but only by finding it ourselves, not from any changelog: `authorization_validity_too_short` on `@circle-fin/x402-batching@2.1.0` was a real SDK/facilitator mismatch, fixed in `3.2.0`.** Original reproduction: funded a fresh EOA with 20 native gas + 20 ERC-20 USDC via `faucet.circle.com` (Arc Testnet), deposited $1.00 into Gateway balance (`getBalances()` confirmed `gateway.available = 1`), then called `GatewayClient.pay()` against our own `gateway.require('0.02')`-gated endpoint. The signed EIP-3009 authorization used `validBefore = now + 345600` (the SDK's own hardcoded 4-day `maxTimeoutSeconds`, matching on both client and server), yet `POST /v1/x402/verify` rejected it as `authorization_validity_too_short`. Root cause, found by diffing `2.1.0` against `3.2.0`'s published source maps (the package ships `.js.map` with `sourcesContent`, which is how we found this without any changelog to read): Circle's real minimum is **7 days**, not 4 — `3.2.0` introduces `GATEWAY_MIN_AUTH_VALIDITY_SECONDS = 7 * 24 * 60 * 60` plus a 100s buffer, and both the client's signing path and the server's `createPaymentRequirements` now use that constant instead of the old hardcoded `345600`. Confirmed against the live facilitator: `GET /v1/x402/supported` on `gateway-api-testnet.circle.com` now explicitly reports `minValiditySeconds: 604800` for `eip155:5042002`. Upgrading to `^3.2.0` was a drop-in fix — no API changes for anything ARCOS calls (`GatewayClient` constructor/`pay()`/`getBalances()`, `createGatewayMiddleware`/`gateway.require()` are unchanged).
- **NEW, and this one's still open enough to be worth flagging: `createGatewayMiddleware`'s `facilitatorUrl` silently defaults to Circle's *mainnet* Gateway API.** After the 3.2.0 upgrade, our quote server (`gateway.require('$0.02')` with no explicit `facilitatorUrl`) started 503-ing every request with `{"error":"No payment networks available"}` — before a payment was even attempted, on the plain unpaid GET. Root cause: `createGatewayMiddleware`'s default `facilitatorUrl` is `https://gateway-api.circle.com` (mainnet); Arc Testnet (`eip155:5042002`) obviously isn't in the mainnet facilitator's supported-networks list, so `getAcceptedNetworks()` filtered down to nothing and the middleware 503'd rather than ever issuing a 402. Fixed by passing `facilitatorUrl: "https://gateway-api-testnet.circle.com"` explicitly (`apps/agents/src/gateway/quoteServer.ts`) — the type comment in `GatewayMiddlewareConfig` documents this default correctly, but it's easy to miss since a testnet chain ID in `networks` reads as "obviously testnet" and nothing in `gateway.require()`'s error path hints that the facilitator itself is scoped to the wrong network. This is exactly the kind of breaking default-change that a one-line CHANGELOG entry (there wasn't one we could find) would have saved us from re-discovering by reading minified source.
- **`GatewayClient` requires a raw local private key with no way to plug in a custom signer.** `GatewayClientConfig` only accepts `privateKey: Hex` — there's no hook for a Developer-Controlled Wallet, a smart-contract wallet, or any external signer to produce the EIP-3009 authorization instead. That's a real tension for a project like ARCOS whose whole pitch is "no agent process holds a raw key": we ended up with one small, purpose-scoped local EOA (holding only a couple dollars of Gateway balance, never treasury funds) specifically to satisfy this SDK's signing requirement, documented clearly as the one deliberate exception rather than something we hid. A `signer`-based `GatewayClientConfig` (viem `Account`/custom EIP-712 signer, not just a raw hex key) would let Gateway-payment buyers keep the same custody model as the rest of a Circle-native stack.
- **Arc Testnet's block explorer (`testnet.arcscan.app`, Blockscout) has real indexing gaps.** We hit multiple transactions that are confirmed on-chain (verified directly via `eth_getTransactionByHash` against the RPC, correct block number, correct sender/recipient) but the explorer permanently returns "we are unable to locate this transaction hash" for them, not just a transient "still indexing, wait 30 seconds" state. This matters a lot for a demo/judging context: a judge clicking a transaction link and hitting a dead end reads as "this project is broken," when the actual transaction is entirely real. We worked around it by treating our own dashboard (which reads state directly from the RPC, not through the explorer) as the source of truth, and added an explicit note in the UI so this doesn't look like our bug. It would be worth Circle/Arc's team looking at why the indexer misses transactions rather than just lagging behind them.
- **Arc Testnet's own primary RPC (`rpc.testnet.arc.network`) rate-limits far too aggressively for anything that scans event history.** Our dashboard reads `DecisionRecorded`/`PaymentCreated` logs via `eth_getLogs` in 10,000-block chunks (Arc's own range cap) from each contract's deployment block. Measured directly: this endpoint returns `{"code":-32011,"message":"request limit reached"}` after as few as 3-5 *sequential* (non-concurrent) `eth_getLogs` calls, which made every cold dashboard load take 30s+ (compounding retries/backoff) or time out outright. We tested the four endpoints listed at `docs.arc.io/arc/references/rpc-endpoints`: `rpc.drpc.testnet.arc.io` handled 90 sequential `eth_getLogs` calls with zero rate-limit errors in the same test where the primary endpoint failed by call #4; `rpc.blockdaemon.testnet.arc.io` returned `{"code":4444,"message":"pruned history unavailable"}` for the exact same range (unusable for a full historical scan); `rpc.quicknode.testnet.arc.io` rate-limited about as hard as the primary. We switched `ARC_TESTNET_RPC_URL` to the dRPC mirror and combined it with durable server-side caching (`unstable_cache` + on-demand `revalidateTag` after each run, `apps/web/lib/chain.ts`) — dashboard loads now take ~1.5-2s instead of 30s+/timeout. This is a significant trap for anyone building read-heavy tooling (dashboards, indexers, analytics) against Arc Testnet using the endpoint that's presented as the primary/default one.

## Recommendations

1. **Fix the `Blockchain` type union in `@circle-fin/developer-controlled-wallets`.** `"ARC-TESTNET"` works fine at runtime but isn't in the exported TS type as of v4.7.0, forcing a cast in `scripts/create-wallets.ts`. This is a small fix with outsized trust cost — a stale type on a brand-new chain is the first thing that makes an integrator wonder if they're holding the SDK wrong.
2. **Put the two-USDC distinction front and center in the Arc docs.** The native 18-decimal gas token and the ERC-20 6-decimal commerce USDC look identical by name but behave completely differently (auto-deducted for gas vs. explicitly transferred via `erc20Abi`). We only found this by diffing `arc-nanopayments/agent.mts`'s use of `parseEther` against its `erc20Abi.transfer` calls. A single callout box on the Arc quickstart page ("there are two USDCs — here's how to tell them apart") would save every new integrator that same detour.
3. **Cross-link the two faucets, or merge them.** `faucet.circle.com` (address-based) and the Developer Console's faucet (wallet-ID-based) solve the same problem for two different audiences but neither page mentions the other exists or explains which one applies to a Developer-Controlled Wallet. A one-line note ("using Developer-Controlled Wallets? Use the Console faucet with your wallet ID instead") on both pages would close this.
4. **Make key SDK reference pages fetchable by non-browser tools.** Several `developers.circle.com` pages (and `npm.com` package pages) returned HTTP 403 to plain `fetch`/`curl` requests during this build, which specifically hurts AI-assisted and scripted development workflows — exactly the kind of fast iteration Circle's SDKs are trying to enable. Serving docs without a browser-fingerprint gate (or publishing a llms.txt / static mirror) would help.
5. **Investigate the Arc Testnet explorer's indexing gaps, and in the meantime add a known-issues banner.** We hit multiple transactions confirmed via `eth_getTransactionByHash` (correct block, sender, recipient) that `testnet.arcscan.app` permanently reports as not found — not a transient "still indexing" state. For a judged/demo context this reads as "the project is broken" when it isn't. Fixing the underlying indexer gap is the real ask; a visible banner acknowledging known gaps (with a link to query the RPC directly) would be a cheap interim mitigation.
6. **Let `GatewayClient` accept a custom signer, not just a raw `privateKey`.** Every other piece of ARCOS keeps agent keys inside Circle Developer-Controlled Wallets specifically so no process holds a raw private key; `x402-batching`'s client is the one place that requirement can't be met as shipped, forcing a small carved-out local EOA. A signer interface (or first-class Developer-Controlled Wallet support) would close that gap for anyone building an agent-to-agent commerce stack fully on Circle's custody model.
7. **RESOLVED as of `x402-batching@3.2.0`, but publish a changelog so the next integrator doesn't have to rediscover this by diffing minified source.** `authorization_validity_too_short` on `2.1.0` was a real mismatch between the SDK's signed window (4 days) and the facilitator's actual minimum (7 days, now exposed as `minValiditySeconds: 604800` from `GET /v1/x402/supported`). `3.2.0` fixes it correctly. We only found this by pulling `3.2.0`'s `.js.map` `sourcesContent` and reading `constants.ts` directly — there's no CHANGELOG.md in the published package and the README doesn't mention it. A one-line changelog entry ("`GATEWAY_MIN_AUTH_VALIDITY_SECONDS` raised from 4 days to 7 days to match the facilitator's actual requirement") would have saved a multi-hour investigation.
8. **Document that `createGatewayMiddleware`'s `facilitatorUrl` defaults to mainnet, and consider making the testnet case impossible to get wrong.** Upgrading to fix item 7 introduced a new failure: our quote server started 503-ing with "No payment networks available" because the default facilitator (`gateway-api.circle.com`) doesn't know about Arc Testnet. The type comment documents the default correctly, but nothing in `createGatewayMiddleware`'s runtime behavior or error message hints that a *testnet* `networks` entry silently paired with a *mainnet* facilitator is the actual problem — the 503 reads like a generic outage, not a config mismatch. Either infer the facilitator from the network(s) passed in (testnet chain ID → testnet facilitator, unless overridden), or have the 503 path say so explicitly (`"eip155:5042002 isn't available on facilitatorUrl gateway-api.circle.com — did you mean gateway-api-testnet.circle.com?"`).
9. **Arc Testnet's primary RPC (`rpc.testnet.arc.network`) needs a materially higher rate limit, or clearer signposting toward the mirrors that don't have this problem.** It rate-limited after 3-5 sequential (not even concurrent) `eth_getLogs` calls in our testing, which makes it unusable for any dashboard, indexer, or analytics tool that needs to scan event history — exactly the kind of tooling a "commerce stack" challenge is trying to encourage people to build. `rpc.drpc.testnet.arc.io` (documented at `docs.arc.io/arc/references/rpc-endpoints`, but not surfaced anywhere in the Arc quickstart alongside the primary endpoint) handled the identical workload with zero errors. Promoting one of the working mirrors to "the" quickstart RPC URL, or fixing the primary endpoint's limits, would remove a real trap for anyone building read-heavy tooling.

Taken together, these are all "day one" friction points rather than deep architectural issues. All four SDKs we integrated (Developer-Controlled Wallets, Bridge Kit/CCTPv2, and the x402-batching handshake on both the payment and settlement side) now work as advertised end to end on Arc Testnet, real money movement included. Every item above cost us a research detour, not a permanent functional blocker — but two of them (the Gateway validity-window mismatch and the primary RPC's rate limit) were severe enough, before we tracked down the fix, to make core parts of the demo look broken rather than "not yet settled." That's exactly the kind of paper cut that's cheap to fix and disproportionately shapes a new integrator's first impression of Arc.
